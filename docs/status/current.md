As of 4 November 2026.

- **Latest result:** the build moved to llvm-mingw (no Visual Studio, Windows SDK or Visual C++ Redistributable). ## Summary

The project is named Motorsport DX since 25 October 2026 (FM4-PC before): the README, the docs, the GUI launcher (`MotorsportDX.exe` since 26 October 2026, `fm4_launcher.exe` before) and the game window carry the new name, while the game's program files (`fm4_rex.exe` and its DLLs), the `FM4_*` variables, the folders and the repository keep the old one as internal names ([why](../analysis/preview.md#4-internal-names)). The project is an experimental build. On the latest binary the e2e harness checks that Quick Race, photo mode and career races run through to their rewards, and that the World Tour runs event after event in one process; the project owner plays Quick Race, career, photo mode and replays on the development laptop and, from exports, on a ROG Xbox Ally X. It is not yet a full port: the full feature set, visuals and stability have not been verified.

- The render path for players is the native path (stages N1 to N6 of the [native port](../analysis/d3d-hle.md)), the default on every computer since 26 October 2026 ([native default](../analysis/native-default.md); with integrated GPUs only from 24 October). It renders races in one pass with 2x MSAA, at the screen's own resolution and aspect (Hor+ on screens wider than 16:9, Vert+ on narrower ones) with a discrete GPU, and compiles no shader or pipeline in play after the launcher's shader pass. RTV (`-Rtv`, the title's PM4 on host render targets) is frozen as the players' fallback: it gets no new features, no gate runs since 27 October 2026 and no smoke before an export since 28 October. `-Rov` stays the uncorrected reference for the EDRAM emulation; its stored captures answer questions about the title's own output, and no gate runs it since 28 October 2026 ([gate tiers](../analysis/d3d-hle.md#gate-tiers-the-main-sessions-decision-of-22-october-2026)).
- The default look is `aces` (`pc` is its earlier name): the project's post passes (GTAO, TAA, the cockpit glass) and shader mods (clear coat, glass, chrome, rims, the road sheen, the cockpit's sky fill). The presets `gt`, `neutral`, `gt7` and `fm2023` share its mods with another tone curve or grade, and `original` is the game's look. AMD FSR 3.1, as native anti-aliasing (`aa=fsr`) and as an upscaler (`-Upscale`), is an option on a runtime built with `-Fsr on`, and TAAU (`aa=taau`) upscales with the project's TAA.
- Controls: the modern pad options (`-Pad`, with the `gameinput` driver and the steering anti-deadzone), the keyboard's steering and pedal model with a racing layout (`-Keyboard`), and native racing wheel support (`-Wheel`, off by default until the owner's hardware test), checked with a virtual pad, a virtual wheel, the ROG Xbox Ally X's built-in pad and injected keys; an Xbox Series controller, the keyboard on the laptop and a real wheel are next.
- The GUI launcher `MotorsportDX.exe` has the racing theme on every page, for pad, mouse and touch, and runs the native path's shader pass after an install or an update.
- The Japan/Asia and USA releases are supported, with Disc 2 and downloadable content (`-Content`).
- Car mods from the player's own FM3 or FM2 discs (`Build.ps1 -Action mods`, `run -Mod`), converted by the separate fm4-content-converter: all 81 FM3-only and 55 FM2-only cars convert, and one car of each raced in a Quick Race ([car mods](#car-mods-5-november-2026)). The GUI launcher's Mods page offers them in a builder install; its conversion has not run from the page yet.
- The build uses llvm-mingw since 1 November 2026: clang 20.1.8 with libc++ and mingw-w64's headers and libraries, nothing of Visual Studio or the Windows SDK, and the game's C++ runtime (`libc++.dll`, `libunwind.dll`) beside it ([setup, toolchain](../setup.md#toolchain)). The build with Microsoft's libraries stays selectable as `-Abi msvc` until the development BuildRoot is converted after the owner's Ally X run.
- A fresh clone of the repository set up, generated and built the game, which ran a Quick Race, on the development computer on 25 October 2026 ([clean setup](#clean-setup-from-a-fresh-clone-25-october-2026)). No second computer has built it from a clone.
- Hardware: the development laptop (Intel Core Ultra 7 255HX, RTX 5070 Ti Laptop GPU) runs every automated test; the ROG Xbox Ally X (Radeon 890M) ran the owner's exports of 24 and 25 October 2026; the export of the Level 1 build (`4a5f02f`) has not run there yet. No other GPU has been tried.
- No original FM4 code or assets, recompiled code, game binaries, saves or captures are in Git, in any commit ([history check](../sources-and-licensing.md#history-check-25-october-2026)). The game content is read from the user's local data.

## Verified on the latest build

### Test environment

- Same Windows computer as development: Windows 11, Intel Core Ultra 7 255HX, RTX 5070 Ti Laptop GPU. The internal 2560x1600 panel at 240 Hz is driven through the iGPU (hybrid mode), and rendering runs on the RTX 5070 Ti Laptop.

- Gate tiers come from [outputs/FM4-build/e2e/matrix.py](../../outputs/FM4-build/e2e/matrix.py). Each run uses a snapshot of the build (`<BuildRoot>\snapshots\<name>`), so the game build can be rebuilt while a gate runs.

| Tier | Contents | Approximate time |
|---|---|---|
| `smoke` | `photo`, `photo_view` and `career` at 240 Hz, one run each | about 10 minutes |
| `perf` | `photo` at 240 Hz, three runs (race phase and photo mode) | - |
| `full` | `photo`, `photo_view` and `career` at 60 and 240 Hz, three runs each | about 1 hour |
| `career` | `career_finish` and `career_progress` at 240 Hz, one run | - |
| `cold` | `career` on empty shader caches, then `photo` on the caches it left, at 240 Hz, one run | about 9 minutes |

The race phase of `photo` is 30 seconds of racing after 10 seconds of driving, with 12 cars. `career` is a World Tour race with quit, replay and continue.

## Known limitations

- **Supported input**: the three XEX executables of the Japan/Asia release (media ID `633772A0`) or of the USA release (`26FF1101`). Their hashes are recorded in [outputs/FM4-build/pipeline.py](../../outputs/FM4-build/pipeline.py). Other regions or revisions, modified executables, a mix of both releases and title updates are rejected. Disc 1 and Disc 2 may be given as extracted folders or as ISOs, which `generate` and the GUI launcher unpack once ([Disc images](../setup.md#disc-images)). The two releases differ only in their executable headers ([release comparison](../analysis/releases.md)).
- **Platform**: Windows x64 only, with a matching toolchain and GPU. Setup checks the prerequisites and does not install Python, CMake, Ninja or llvm-mingw (the `toolchain` action fetches portable copies on request); the default build needs no Visual Studio. A clone alone is not a playable game package. See [setup](../setup.md).
- **Save data**: saves and progress from historical builds loaded. Compatibility of all saves and profile migration between builds or computers is not guaranteed. The workflow uses its own local profile and does not copy old saves automatically.
- **Profile state in e2e**: on 14 October 2026, three runs with a new, empty profile did not reach a race in the harness. The game then shows the default car and different pre-race screens, which the harness did not recognize. With a copied profile and shader cache, 6 of 6 runs reached the race. The e2e scenarios therefore use `--profile copy`. The same holds for `warmcache`: on the new profile of a clean BuildRoot (25 October 2026) the game played its long intro video after the title, and the timeline timed out waiting for PLAY CAREER; [running](../running.md#shader-cache) now says to play once first. See [e2e overview](../e2e/README.md).
- **Harness menu navigation**: the game ignores the first press after several screens open. The career menu and `GO RACE` also hide about 9 seconds after the last press (a real-time timer, not a frame count). The e2e scenarios press until OCR reads the expected screen, instead of counting presses.
- **Developer AI driver**: `engageaionstart` (rebuilt on 16 October 2026) is a test tool, not a player feature. `matrix.py` uses it by default unless `--human` is given. Direct launch into a race is not available, because the code that reads the `track`, `car` and `launch` options is missing from the retail build.
- **Fixed seed for the race setup**: `FM4_FIXED_SEED=<n>` (21 October 2026, off by default; see [experiments](../e2e/experiments.md#fixed-seed-for-the-race-setup)) keys SQLite's random generator at the opponent cars query and pins the AI drivers' seeds. Verified the same day on one binary (sha256 `27f90c57...`, the `freeze` scenario at 2x with `engageaionstart`): two runs with `FM4_FIXED_SEED=1` showed the same opponent cars and the same grid slot (the same station wagon ahead); two runs without it showed other cars and other slots, draws per frame 3,320.2 and 3,195.6 (3.8% apart), 56.0% of the pixels above 4. Seeded freeze runs still differ in their frozen frame, not because of the race setup: with the rewind's first press pinned to race frame 720 (counted in pad polls then), four seeded runs differ in 19 to 34% of the pixels, because the race advances by wall time ([frozen frames](../e2e/frozen-frames.md#baseline-variance); the earlier seeded pair is in [history](history.md#21-october-2026-frozen-frame-variance-with-presses-on-the-wall-clock)).
- **Fixed frame time for races**: `FM4_FIXED_FRAME_TIME=1` (21 October 2026, off by default; see [experiments](../e2e/experiments.md#fixed-frame-time-for-races)) turns on the title's `lockupdatetimeto60fps` (every main loop pass one step of 0.01668335 s instead of the measured time) and starts the 3-2-1 60 session updates after the countdown placed the cars; with `FM4_FIXED_SEED` the cars' random states are reset at the 3-2-1. The diagnostic controller now counts race frames in session updates, not pad polls. Verified the same day on one binary (sha256 `90179f8d...`): two `freeze` runs with both switches started the 3-2-1 and pressed Y on the same session updates and agreed within 0.2% in draws and predicated packets, but their frozen frames still differ in 25.64% of the pixels: the race diverges from a last-bit difference while the AI revs before the start, whose input is not found, and the crowd differs ([what pinning the moment needs](../e2e/frozen-frames.md#what-pinning-the-moment-needs)). `parity.py` keeps its 60% image limit.
- **Shadows**: with the workaround off (the default), the shadow map is rendered on all race cameras. Its parity with the original Xbox has not been compared.
- **Stubs**: some Xbox and runtime service functions are still stubs. The synthetic instruction tests do not prove that the kernel, audio, timing, synchronization or shaders are correct.
- **Synthetic tests**: the 295,650 instruction checks and 5 script tests use synthetic data. They do not prove that the game behaves correctly.

## Open issues

- **Sun glare strength depends on the MSAA level.** Matching the original Xbox glare is not a goal (decision of 18 October 2026): the glare is to look good and stay the same at every quality setting. The sun query counts guest samples, in proportion to the MSAA sample count, and the glare does not follow the count linearly. The `sun` look knob (`sun=2` in every preset but `original`) turns the awaited reports into guest pixels times the strength, through a soft limit of 1,200 pixels, so in an A/B with fixed counts 340 samples at 1x and 1,360 at 4x give the same medium star ([sun glare](../running-look.md#sun-glare)). Races with real counts at `high` quality were not compared with and without the knob. The measurements are in [results history](history-results.md#sun-glare-measurements-18-october-2026).
- **Full-frame occlusion on RTV**: the full-frame query used for auto-exposure reports about 1.5 times the ROV sample count, because the host query counts every sample that passes. No visible effect was seen. The auto-exposure query was not changed.
- **Missing road pieces (mitigated, not fully explained)**: on some runs of the RTV path, road pieces (mostly on the start straight, 4-14 seconds after the start) were not drawn and showed the flat clear color (102,102,102). Kerbs and other objects were still drawn. The cause was found on 15 October 2026. The loader's sGPU heap could not place a 1.8 MB section because the heap was fragmented after a load spike. The loader then failed and discarded the request. The fix is a fallback: when the sGPU allocation fails, the section is retried from fGPU. Set `FM4_STREAMING_FALLBACK=0` to turn it off. See [work/fm4-rex/src/fm4-streaming-fixes.cpp](../../work/fm4-rex/src/fm4-streaming-fixes.cpp). After the fix, 20 of 20 runs with fixed vblank (the more frequent failure case) showed no missing road, and 5 of those runs used the fallback successfully. Three Quick Race runs with the current defaults also showed no clear-gray frames. The e2e harness detects the symptom through `clear_gray_frames`.
- **Tiling quality versus speed on RTV**: on RTV, one tile without MSAA is the default with TAA since 20 October 2026 (the project owner's choice); the native path renders races in one pass with 2x MSAA instead. It takes 19 to 26% fewer draws, 60 to 68% fewer predicated packets and 0.5 to 0.6 ms less GPU time per race frame at 1x than the tiles of `high`, and at 2x about 1 ms less GPU time (19 October 2026, [TAA, MSAA and tiling](../analysis/taa.md#5-msaa-and-tiling)). Without MSAA a still picture has no anti-aliasing unless the jitter runs, so a still camera is jittered and TAA accumulates its phases ([one tile with TAA](history-results.md#one-tile-with-taa-the-presets-and-taas-history-20-october-2026)). Not yet checked with the fixed history: thin wires and fences in motion at 2x, which TAA alone must hold without MSAA. On ROV (3 runs, 14 October 2026) `-SingleTile` raised fps from 54.3 to 58.6; without TAA (FXAA) thin wires break up.
- **Ambient occlusion scope**: AO is missing in the cockpit interior (the depth range is compressed there) and in the small car view of the car select screen (narrower than the scene depth's minimum width). The garage's full-screen car views, Autovista and the career home have it since the camera fallback of 19 October 2026. See [GTAO design](../analysis/gtao-design.md).
- **An "Ally X performance" look preset (candidate)**: on the ROG Xbox Ally X's 890M, GTAO takes 0.7 to 0.9 ms and the windshield pass 0.6 ms of a 7.5 to 8.3 ms race frame at 1x ([17.25](../analysis/d3d-hle-n4.md#1725-the-second-rog-xbox-ally-x-run-24-october-2026)); a preset without them, or a cheaper windshield, would give that back on battery. The windshield costing almost as much as GTAO is worth a look.

## Current gaps

Everything still open, grouped by area.

### Display

- The `sun` knob keeps the sun glare the same at every MSAA level, checked with fixed counts only (see [Open issues](#open-issues)). `-Look original` and `-Rov` keep the glare that changes with the MSAA level.
- AO is not in the cockpit interior. It runs in the garage's full-screen car views, Autovista and the career home (checked on 20 October 2026, [AO outside races](history-results.md#ao-in-the-garage-autovista-and-the-career-home-20-october-2026)); at 0.6 it turns the brake disc behind the spokes almost black in Autovista. See the "Later" section of [GTAO design](../analysis/gtao-design.md).
- The cockpit interior is near black on sunny parts of the Bernese Alps (dashboard top 0.1 to 3 of 255, gauges 1 to 6 at 2x). Measured on 19 October 2026 with frozen frames: RTV and `-Rov` match within a few levels with `-Look original`, there is no transient after a camera switch, and in tunnels the interior is readable. It is the game's interior lighting: its own shadow map shades it, `MinCockpitShadow` is 0, and the ambient term is small against an exposure set by the snow outside. The `pc` look darkens it by 15 to 35% more through ACES; AO does not reach it. The presets' `cockpit_fill=1` (since 26 October 2026) lights the shaded interior with a sky fill from the game's hemispherical term, steady with the sun ahead, beside or behind and the game's own in tunnels; the earlier floor `cockpit_light` swung with the sun's direction ([Cockpit sky fill](history-results.md#cockpit-sky-fill-26-october-2026)). A cockpit exposure of +2 stops blows out the windows. The windshield and side windows look open in the cockpit camera because the title draws no window glass for the player's car in that camera (only in the 3-2-1 camera); the `windshield` post pass (1 in `pc`) adds it. See [cockpit brightness](../analysis/cockpit-brightness.md).
- Look mod coverage is partly verified in the game (17 October 2026, [look mod coverage](../analysis/look-mod-coverage.md#in-game-checks-17-october-2026)): false-color runs show the body paint mods of races, replays, the cockpit, car menus, HomeSpace, Autovista (the showroom) and the 16-car and split-screen car shader sets on screen. The 16-car and split-screen sets were loaded in a Quick Race through `FM4_RACE_SETTINGS`. On 18 October 2026 the title's 16-car render scenarios were reproduced at `-Quality xbox` on a 12-car grid (Quick Race has no 16-car grid), and photos at shutter speed 0 and 100 (also one from a replay) were saved; `REX_GPU_INVENTORY` showed no new hash. A real split-screen race and a real 16-car grid were not run. The second body paint technique of each set, the four watermark final combines, the no-post-effects final combine and the three photo motion blur variants never showed in any run, so their mods are checked by compilation only. `E5B1A71249D0CA9A`, first thought to be the environment cube render, draws the car lights and trim, so it needs no clear coat.
- The glass, chrome and rim mods (`-Look glass`, `chrome`, `rims`; 31 hashes of the race, 16-car, split-screen and garage car shader sets) are in `pc` since 20 October 2026. The A/B at 2x on the Bernese Alps grid with the camera turned toward the sun showed a little more reflection on the windows and no highlight blob on glass or chrome ([facing the sun](../analysis/look-mod-coverage.md#facing-the-sun-and-the-pc-preset-20-october-2026)); the split-screen set, the chrome rims on screen and other tracks and times of day were not seen. The spinning-wheel blur shaders, the chrome with a normal map, the showroom set and the material shaders that load in the UI only have none. See [look mod coverage](../analysis/look-mod-coverage.md#glass-chrome-and-rims-18-october-2026).
- The sky and vegetation mods (`-Look sky_*` and `foliage_*`; 15 hashes: the race sky dome, trees, tree cards, bushes and grass of every race track) are in no preset. False color and an A/B at 2x covered the Bernese Alps and Maple Valley at one time of day. The HomeSpace skies, `DIFF_TREEBEND_1` (trunks and branches) and the terrain under the grass have none, and 5 of the 15 hashes did not draw on these two tracks. See [look mod coverage](../analysis/look-mod-coverage.md#sky-and-vegetation-18-october-2026).
- The road surface mods (`-Look road_*`; 25 hashes: the road shaders of 20 race locations, the painted lines, the road edges and the paved shoulders) are in every preset but `original` as `road_specular=0,road_sheen=0.4` (in `pc` since 20 October 2026): the game's near-white sun highlight on sunlit asphalt toward the sun gives way to a grained sheen. The roads of Amalfi, Fujimi Kaido and Maple Valley are drawn by terrain, shoulder and track object shaders, so they keep the game's highlight; Indianapolis and Infineon (`2AD313C93939CC4E`), the shoulders of Tsukuba and the other `SHLDR_*` hashes have no mod, and the A/B ran at one time of day. The measurements are in [results history](history-results.md#road-surface-look-mods-in-detail-18-to-20-october-2026) and [look mod coverage](../analysis/look-mod-coverage.md#the-sheen-on-top-gear-and-its-grain-18-october-2026).
- The track lighting knobs `road_gloss` and `sky` (`FM4_TRACK_SETTINGS`, see [track lighting](../running-look.md#track-lighting)) work in the game: every preset but `original` sets `sky=0.7` (a bluer, less washed out sky that keeps the snow and clouds bright), and no preset sets `road_gloss`, which does not remove the sunlit road's sheet. The runs of 18 October 2026 are in [results history](history-results.md#track-lighting-knobs-in-the-game-18-october-2026).
- Parity with the original Xbox (shadows, color, reflections, noise and object edges) has not been compared. The combinations of MSAA and render scale are not all verified.
- The post pass framework (18 October 2026) gives screen passes at three points of the frame, history textures, camera reprojection, per-car motion vectors, the jitter of the scene draws and a write-back into the game's scene, and has GTAO, the motion vectors and TAA ([post pass framework](../analysis/post-pass-framework.md)); rain screen effects and screen-space reflections are not written yet, and AMD FSR 3.1 is the temporal upscaler since 25 October 2026 ([FSR plan](../analysis/fsr-plan.md); see [post pass framework](../analysis/post-pass-framework.md#the-final-point-and-upscalers)). The motion vectors (host-built from the game's resolved depth, its stencil object IDs and the car and camera matrices of the vertex shader constants; [motion vectors](../analysis/motion-vectors.md#8-implementation-18-october-2026)) are verified in the game; the cockpit interior, the world through car glass and the rear-view mirror panel are handled with a mask. Wheel spin and the steering wheel and hands take the motion of their car or interior. Not traced: a 16-car grid, and what sets the scale k of the game's matrices.
- TAA (19 October 2026; [TAA, current state](../analysis/taa.md#current-state)): every preset has TAA at the final point, before the HUD, with `TAA_SHARPEN` 0.4 (none in `original`) and one tile without MSAA; the scene is jittered while the camera moves at 45 fps or more and on a still camera, whose still pixels accumulate the phases ([one tile with TAA](history-results.md#one-tile-with-taa-the-presets-and-taas-history-20-october-2026)); `-Look "aces,taa=0"` turns it off and `-Look "aces,taa_point=1"` runs it at the scene_color point instead, as an option. From step 7 (19 October 2026, 20:25) until 20 October 2026 neither point had a history in the game, so TAA's own anti-aliasing was not in effect then ([TAA, the history defect](../analysis/taa.md#the-history-defect-19-to-20-october-2026)). It costs about 0.2 ms of GPU time per race frame at 2x (0.47 ms at the scene_color point), passed the smoke and perf gates and the Japan/Asia check, and the scene camera behind it is known on all 26 environments of the TRACKS screen and in replays. There is no reactive mask for particles and the interior mirror; nothing ghosted in the checks so far.
- Texture replacement (`-TextureDump`, `-TextureReplace`; 19 October 2026) works on the Bernese Alps: a Quick Race dumps 969 textures, the sky panorama (`5de3b416781cfd97`, DXT1 8192x2048) keeps its hash across runs, and a test pattern in its place shows in 2x captures and in the car reflections. The smoke gate with both switches on passed 3 of 3 cells against the same binary with them off (`career` PASS, `photo` and `photo_view` WARN on capture statistics). See [texture replacement](../analysis/texture-replacement.md#verification). Open: no real replacement art yet; no other track, the HomeSpace or the garage dumped; replacements load on the command processor thread, which a large pack would make stutter; render targets, cube maps, arrays, 3D textures and textures that change all the time are not covered. The offline extractor (`texture_extract.py`, 19 October 2026) dumps the textures stored in the 32 track archives without running the game: 18,473 distinct hashes, among them a sky panorama for every race track (tiles on Road America and Silverstone). Its Bernese Alps sky is byte-identical to the runtime's dump, and 103 of its 493 Bernese Alps hashes are in the runtime dumps of that track; the textures streamed from the `.bix` files (8,300 records) and cube maps are not extracted ([offline extraction](../analysis/texture-replacement.md#offline-extraction)).
- Not done: post-process anti-aliasing other than TAA and FSR 3.1 (SMAA, or FXAA without `-SingleTile`), HDR10 output (design: [HDR output](../analysis/hdr-output.md)), new lighting for tracks (beyond the `TrackSettings` knobs), car materials other than paint, glass, chrome and rims (tires, brakes and lamp lenses; the cockpit interior has only the `cockpit_fill` sky fill and the `cockpit_light` shadow floor), track surfaces other than the road, its lines, edges and paved shoulders (terrain, kerbs, grass), and car flake paint. Flake cells in UV space are too small for race cameras and need an LOD model.
- Wide and tall screens: the native path renders the screen's aspect since 25 October 2026, Hor+ wider than 16:9 and Vert+ narrower, with the HUD and the menus in the centred 16:9 ([D3D-level HLE, 18.24](../analysis/d3d-hle-n5.md#1824-increment-2s-close-gate-25-october-2026)). RTV and `-Rov` keep a 16:9 image with bars; so do the integrated GPUs' automatic 1x, `-Supersample` and `-ResolutionScale 1` to `4`.
- The front-end menus, Autovista, the career home and photo mode render at the screen's scale on the native path since 26 October 2026 (`-Entry0 s`, the default with `-Native` in one pass 2x; the pre-race screens were already there), and the menus, Autovista and the career home run GTAO at fractional scales and logical sizes too. Photo mode runs its scene passes there too since a later change of the same day; its saved photo at a logical size is the centred 16:9 part of the picture ([D3D-level HLE, 18.28](../analysis/d3d-hle-n5.md#1828-the-saved-photo-at-a-logical-size-27-october-2026)). `-Entry0 k` keeps all of them at the whole scale, scaled to the screen ([D3D-level HLE, 18.26](../analysis/d3d-hle-n5.md#1826-entry-0-at-s-with-photo-mode-in-its-three-tiles-26-october-2026) and [D3D-level HLE, 18.27](../analysis/d3d-hle-n5.md#1827-photo-modes-tiles-at-the-scenes-scale-and-at-a-logical-size-26-october-2026)).

### Performance

- On the native path at 2x the race is limited by the GPU (5.02 ms a frame in the soak, 194.8 fps at 240 Hz); at 3/2 it is close to the 240 Hz limit ([current performance](#current-performance)).
- The reward and gift car screens of the career hold frames of 150 to 381 ms, no shader work: the title's own compression of the profile's save and a new car's first draw. The main session's decision of 30 October 2026 leaves them ([career season soak, 9](../analysis/career-season-soak.md#9-the-reward-screen-hitches-30-october-2026)).
- The ROG Xbox Ally X has not run the render thread's idle wait yet, which is on by default since 31 October 2026 (the owner's A/B, [render thread idle wait](#render-thread-idle-wait-30-and-31-october-2026)).
- The race clock does not run faster above 60 Hz (ratio 1.001). But lap time and handling are not yet compared between 60 and 240 fps.
- Level 1 of the native port (no shader or pipeline compiles in play) passed its final gate on this PC, but has not run on the ROG Xbox Ally X yet. The owner's runs of the export of `4a5f02f` will decide whether N6's item 2 (direct D3D12 draws) is taken up, and whether the pipeline library stays on by default ([D3D-level HLE, 19.11](../analysis/d3d-hle-n6.md#1911-the-level-1-final-gate-29-october-2026)).

### Stability and runtime

- Handles leak slowly: the host Thread handles and Events of guest threads that have exited are not closed, about 15 a race and linear (about 500 in 3 hours, harmless at that rate). The fix is left to a runtime session ([revisit soak](#revisit-soak-and-the-title-render-thread-30-october-2026)). Memory and GPU memory are caches that stay level once tracks and cars come back.
- The XAM and kernel stubs are listed for the career ([career season soak, 7](../analysis/career-season-soak.md#7-kernel-and-xam-stubs-called)); Quick Race, photo mode, replays and DLC content are not.
- Save compatibility between builds and profile migration between computers are not guaranteed.

### Platform and distribution

- A fresh clone ran the full workflow on the development computer on 25 October 2026 ([clean setup](#clean-setup-from-a-fresh-clone-25-october-2026)), not yet on a second Windows computer. The llvm-mingw build (since 1 November 2026) has not run on a computer without Visual Studio, or on the ROG Xbox Ally X. [Exports](../running.md#export-to-another-computer) of the GUI launcher ran on the ROG Xbox Ally X from 24 October 2026.
- Tested GPUs: the RTX 5070 Ti Laptop and the Ally X's integrated Radeon 890M. Other NVIDIA GPUs, AMD and Intel discrete GPUs, desktops, Windows 10 and lower-end CPUs have not been tested.
- Only the Japan/Asia and USA releases are supported. The European release and title updates are not. The European discs have not been compared with the other two. A title update relinks the executable, so supporting one needs a second integration profile and a runtime fix for the USA v4 module patches ([title updates](../analysis/title-updates.md)).
- The third-party licenses were reviewed for a preview on 25 October 2026 and every license text is in the notices; the project's own code is under the BSD 3-Clause License since 27 October 2026, two vendored files state no license, and `XenonRecomp-FM4-fixes.patch` is still pending ([open items](../sources-and-licensing.md#open-items-before-a-public-release)). What a preview can be and its checklist are in the [preview plan](../analysis/preview.md). There is no CI. The builder package (B6) builds the game through its launcher on this PC; it has not run on a second computer and is not published.
